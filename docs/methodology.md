# 分析方法与输出解释（analysis/）

本文件说明 `analysis/` 如何把 `inputs/` 的原始观测转成项目组可用的可达性
与项目比较结果。所有结论都是**带假设与不确定性的分析输出**，不是业务承诺；
原件不被修改，结果统一写入 `outputs/`。

运行：

```bash
python -I analysis/__main__.py inputs outputs
python -I tests/test_analysis.py          # 分析层单元测试
python -m unittest discover -s tests -v   # 含原件物理校验的全部测试
```

## 1. 情景轴（共同情景，不逐项目挑参数）

- 网络状态：基线、L1 恢复未兑现、L1 全天失效压力测试、P1/P2/P3 各自施工与
  完工、P1+P2 组合施工与完工、两个敏感性变体（双向封闭、P3 双向坡改）。
- 需求情景：人口三档（按 origins 25–40 人区间相对名义 30 人缩放）× R1 两个
  可能出口（R1、R1-alt），共 6 个，对所有网络状态固定使用同一组。

## 2. 物理可行性（feasibility.py）

按 profiles 的宽度、台阶、坡度阈值逐层过滤：

- 台阶：`steps_allowed=False` 的轮椅与缓坡群体不能走 e3/e3r；
- 宽度：轮椅要求 ≥1.2m，e5/e5r（1.1m）被挡，P3 只改坡度故轮椅仍不可用；
- 坡度：契约规定上坡正值受限；下坡契约未规定，分析按同一绝对值阈值作
  安全假设（见 config.ASSUMPTIONS），并在证据登记中可追溯；
- 梯边还需电梯在到达时刻处于开放窗口且不在停运区间。

## 3. 用时证据处理（travel.py）

- `completed`：按边 × 群体拟合对数正态用时；
- `observation_end`：右删失，只作为真实用时的下界，不并入均值；若删失值
  超过拟合 p90，则把 Monte Carlo 抽样的保守端拉到该值；
- `turned_back`：作为该边对该群体不可独立完成的证据，不产生用时分布；
- 无观测边（如 e11 的轮椅、两条新建边）**绝不按零分钟**：依次尝试反向同段
  转移、同群体秒/米速度模型外推、保守先验带，全部标记 `weak` 并登记原因；
- 新建边：电梯边类比 e4 轿厢用时、普通边用速度模型外推并加宽预测带，
  source 分别为 `lift-analog` / `speed-model`，明确不是实测。

## 4. 时变路径与联合电梯排队

- FIFO 时间依赖 Dijkstra，边权随出发时刻变化；
- 电梯先到先服务，按 `capacity`/`cycle_seconds` 做**跨全部请求组、全部出发
  时段的联合排队**：候梯时间取决于全体居民的共同路径选择，而不是各组单独
  排队。停运区间内的计划梯次顺延到恢复时刻，闭门前无法乘梯记为不可行；
- 路径选择与候梯表做不动点迭代（路由→梯前到达→排队→再路由），直到路径
  集合稳定或达到迭代上限；
- 同一请求组到不同服务点的备选路径共用一部梯时只计一次到达，避免重复占票。

## 5. 可靠度与服务窗口（scenarios.py）

- 出发窗口按 5 分钟切片，每片等人数份额；
- 固定不动点路径后做 400 次 Monte Carlo（每条边×群体预抽、跨情景复用，
  种子固定可复现），逐片估计在 `max_total_seconds` 内且在服务窗口内到达的
  概率，再按份额加权为该请求组到该服务点的可靠度；
- 早到服务点计入等待开门时间，不直接判失败；关门后到达或超时限判失败；
- 可靠度 ≥0.80（config.RELIABILITY_THRESHOLD）才进入容量分配，门槛本身是
  分析约定，可在配置中调整后重跑。

## 6. 服务容量分配（allocate.py）

可达不等于可接待。两级 MILP：先最大化窗口内总接待人数，再在不减少总量的
前提下向弱势（轮椅权重 3、缓坡 2、普通 1）与高可靠度倾斜。另用透明贪心
独立求解并同时输出，两者总量差异会暴露在结果中而非被隐藏。

## 7. 输出文件

| 文件 | 内容 |
| --- | --- |
| `scenario_metrics.csv` | 网络状态 × 需求情景的名义需求、可靠可达人数、MILP/贪心服务量、未满足需求、分群体服务量 |
| `route_evidence.csv` | 每个请求组到每个服务点的路径、各出发时段路径占比、可靠度、p50/p90 总用时、弱证据边、失败原因 |
| `evidence_gaps.csv` | 无完成观测、折返、纯假设（新建边/情景假设）的登记条目 |
| `comparison_summary.json` | 预算约束、结构性容量缺口、P1/P2 互补性、分群体挤出、各状态服务量与施工损失、全部假设清单 |

施工损失有两个口径，不能只看服务量：

- `construction_window_loss_persons` × `construction_days`：服务量口径，即窗口内
  接待人数下降按工作日折算；当封闭边存在替代路径时该值可能为 0；
- `construction_reachable_delta` 与 `construction_mean_reliability_*`：可靠度口径，
  捕捉“仍有人能到但用时变长、部分出发时段失败”的退化。例如 P3 施工封闭 e5 后
  缓坡群体平均可靠度显著下降，但总服务量未必立刻变化。

## 8. 可以解释与可以重跑的边界

- 每条受益都能回溯到具体路径边、出发时段与容量假设（route_evidence 的
  weak_edges 与 fail_reasons）；
- 现场补测后用新观测重建 inputs（保持契约字段），或确认 L1 恢复后改 actions，
  同一脚本即可重新比较；
- 分析不自动派单、不输出唯一必选项目，只给服务范围、未满足需求与证据薄弱点。

## 9. 数据覆盖边界（如实声明）

- 本批 `requests` 的类别全部是 `meal`，因此 9 个请求组只评估到 S1/S2；
  卫生服务点 H1（clinic）在网络与窗口数据中存在，引擎也已按类别匹配实现
  （出现 clinic 类请求即自动纳入 H1 评估），但当前没有 clinic 需求记录，
  故不产出 H1 的可达性结论——不能用零需求冒充“无人需要”。
- `planning-context.json` 的 `construction_departure_window=2` 契约未定义语义，
  分析不使用其数值，仅在假设清单（config.ASSUMPTIONS）登记。
- 项目 `new_edge` 为单向；返程可用性不在数据中，分析不虚构反向边，只在假设
  清单提示这一限制。
